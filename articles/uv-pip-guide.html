用 uv 管理 Python：环境、依赖与复现

发布于 2026-01-06更新于 2026-10-15Python 工具
文章目录

一个 Python 程序能否运行，取决于使用哪个解释器，以及这个解释器能找到哪些依赖。uv 可以下载 Python、创建虚拟环境、安装依赖，也可以管理项目的依赖声明与锁文件。先分清这些对象，才容易判断一条命令会改动哪里。

解释器、环境与依赖文件

对象作用需要分清的边界
Python 解释器执行 Python 代码版本会影响语法和依赖兼容性
.venv隔离项目安装的第三方包通常仍引用基础解释器，不是可随处搬运的 Python 副本
requirements.txt记录包及版本要求文件是否完整、是否固定版本，取决于生成方式
pyproject.toml 与 uv.lock记录项目声明与解析后的依赖用于 uv 的项目管理流程

虚拟环境解决依赖隔离问题，依赖文件解决环境重建问题。只保存其中一个，换机器或换目录时仍可能缺少必要信息。

先选定依赖管理方式

已有 requirements.txt，或希望直接维护虚拟环境时，可以使用 pip 接口：uv venv、uv pip install、uv pip compile 和 uv pip sync。

希望由项目文件统一管理 Python 版本和依赖时，可以使用 项目模式：uv init、uv add、uv run 和 uv sync。普通脚本项目、应用和需要发布的包都可以采用这种方式。

下面先完成 pip 接口的流程，最后给出项目模式的对应操作。同一个环境里混用两套命令时，要明确哪份文件负责记录依赖。

安装 uv

macOS / Linux：

curl -LsSf https://astral.sh/uv/install.sh | sh

Windows PowerShell：

powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

安装后重新打开终端，验证：

uv --version

独立安装器不要求预装 Python。也可以从 官方 Releases 下载符合操作系统和处理器架构的压缩包，把 uv 或 uv.exe 放入 PATH 包含的目录。

下载好 uv 只解决工具本身的安装。完全离线的机器还需要提前准备 Python 解释器和依赖包，不能依赖后续的自动下载。

创建环境并运行代码

在项目目录执行，示例统一使用 Python 3.12：

uv venv --python 3.12
uv pip install --python .venv requests

第一条命令创建 .venv。uv 会查找合适的 Python；未找到且允许下载时，会下载所需版本。第二条命令将 requests 及其依赖装入这个环境。这里显式指定 --python .venv，避免终端中激活的其他环境影响安装位置。

macOS / Linux 使用环境中的 Python 验证安装：

.venv/bin/python -c "import sys, requests; print(sys.executable); print(requests.__version__)"

Windows PowerShell：

.\.venv\Scripts\python.exe -c "import sys, requests; print(sys.executable); print(requests.__version__)"

输出的解释器路径应位于当前项目的 .venv 中，并显示 requests 版本。运行自己的脚本时，将 -c "..." 换成脚本路径即可。

虚拟环境的选择顺序

省略 --python 时，uv pip install 等修改环境的命令会依次查找：已激活的虚拟环境、已激活的 Conda 环境、当前目录或最近父目录中的 .venv。

uv venv new_env 可以创建自定义目录，但 uv 不会根据这个名字自动选中它。需要激活该环境，或使用 uv pip install --python new_env requests 这样的显式路径。

记录依赖，再决定安装还是同步

已有一个工作正常的环境时，可以导出当前安装状态：

uv pip freeze --python .venv > requirements.txt

freeze 会列出当前环境中已安装的包及版本，包括间接依赖。导出前应确认环境只包含项目需要的内容；这份快照也不保证适用于所有操作系统和 Python 版本。

需要持续维护直接依赖时，可以在 requirements.in 中每行写一个包名，例如：

requests

再解析完整依赖并同步到环境：

uv pip compile --python .venv requirements.in -o requirements.txt
uv pip sync --python .venv requirements.txt
uv pip check --python .venv

compile 解析直接依赖和它们依赖的其他包，并把版本写入输出文件。通常提交 requirements.in 与生成的 requirements.txt，让后续安装有据可依。

命令对现有环境的影响适用情况
uv pip install --python .venv -r requirements.txt安装文件中的要求及其依赖，保留无关的已安装包需要补充依赖，不要求清理环境
uv pip sync --python .venv requirements.txt按清单安装，并删除清单以外的包使用包含间接依赖的完整清单重建环境
同步前确认清单完整

uv pip sync 不会替清单补齐遗漏的间接依赖。把只写了 requests 的文件直接交给它，可能得到缺少依赖的环境。应使用 compile 生成的完整清单，或经过确认的环境快照；执行前也要知道，清单以外的包会被删除。

移动项目时重建环境

保存源码和依赖文件，换到新目录或新机器后重新创建 .venv。虚拟环境中的脚本可能记录旧解释器的绝对路径；复制环境后，Python 导入成功也不能证明所有命令都能工作。

在不含旧 .venv 的目标项目目录执行：

uv venv --python 3.12
uv pip sync --python .venv requirements.txt
uv pip check --python .venv

这里的 requirements.txt 应是完整清单，并适用于目标平台和 Python 版本。uv pip check 检查依赖兼容关系，不检查脚本是否仍引用旧路径，最后还需运行项目自己的启动命令或测试。

.venv 应加入 .gitignore。如果卸载 uv 管理的某个 Python 版本，也要先确认现有虚拟环境没有继续依赖它。

使用项目模式时怎么做

在另一处目录创建新项目，避免与上面的 pip 接口示例共用环境：

uv init --python 3.12 my-app
cd my-app
uv add requests
uv run python -c "import requests; print(requests.__version__)"

uv add 把直接依赖写入 pyproject.toml，解析结果记录在 uv.lock，并更新项目环境。共享项目时，提交源码、pyproject.toml、uv.lock 和 .python-version。

在另一台机器取得这些文件后执行：

uv sync --locked

--locked 要求锁文件与项目声明一致；不一致时会报错，提醒先处理依赖记录。项目模式默认使用项目自己的 .venv，即使终端激活了另一个环境，也不会默认改用它。

在能发现项目文件的目录中，uv run 默认先检查锁文件并同步依赖，因此可能调整已安装包的版本。它默认保留不冲突的额外包；uv sync 默认会清理项目未声明的额外包。直接使用 uv pip install 安装的包不会自动成为项目依赖，需要通过 uv add 记录。
